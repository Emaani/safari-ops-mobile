Sync & Robustness Audit

A follow-on review triggered by the payment transaction ID fix — once one client duplicated a server-side rule and drifted from the web dashboard, we checked whether the same pattern recurs elsewhere. It does, twice over, plus a handful of standalone robustness gaps.

13 findings 2 live bugs already in production Generated 10 Oct 2026

The pattern behind this audit

The payment bug wasn't really about payments — it was about a business rule living in two places at once: mobile wrote bookings.amount_paid directly while the web dashboard went through a shared record_payment function, so the two clients could quietly disagree about a booking's balance and transaction history.

That exact shape of bug — client-side logic that should be one server-side rule, instead reimplemented per screen — recurs in vehicle status transitions and cash requisition approvals. The vehicle case has already produced a live bug, not just a risk. The rest of this report covers unbounded queries, redundant realtime subscriptions, and a few smaller robustness gaps that surfaced along the way.

Safari-booked vehicles never return to "available"SafariManagementScreen.tsx:518

When a vehicle is assigned to a safari booking, saveOps sets the vehicle to booked — but there is no matching write anywhere that ever sets it back to available when the safari completes or is cancelled. Compare this to the vehicle-hire flow in EditBookingModal.tsx, which explicitly releases the vehicle on Completed/Cancelled. The safari flow has no equivalent, and the write is wrapped in a silent catch {'{'}/* non-fatal */{'}'} that would hide a failure even if one were added.

ImpactEvery vehicle assigned through Safari Management's Operations tab is permanently stuck as "booked" in Fleet once that safari ends — it can never be assigned to anything else until someone manually flips it back from the web dashboard or a database console.

New booking marks vehicle "booked" even when created as Cancelled/CompletedNewBookingModal.tsx:931

STATUS_OPTIONS lets staff create a booking directly as Completed or Cancelled (useful for backfilling historical records) — but the vehicle-assignment write at line 931 unconditionally sets the vehicle to booked whenever one is attached, with no check against the chosen status. EditBookingModal.tsx documents the correct rule ("Completed/Cancelled → available, else → booked") but NewBookingModal never applies it.

ImpactBackfilling a completed historical booking with a vehicle attached locks that vehicle as unavailable in Fleet, even though the trip it was "booked" for is already over.

Vehicle status rule is copy-pasted three times, and has already drifted3 files

The "what should a vehicle's status be after this booking write" rule is implemented independently in NewBookingModal.tsx:931 (always booked, no release logic at all), EditBookingModal.tsx:351-366 (the fullest version — releases on Completed/Cancelled, releases a swapped-out vehicle, releases on unassignment), and SafariManagementScreen.tsx:518 (only ever sets booked, gated on the vehicle's current status, never releases). Three copies, three different behaviors, in the same app.

ApproachMove this rule into a Postgres function — mirroring exactly what record_payment already does for the payment case — triggered off booking-status changes, so web and mobile both get vehicle availability right by construction instead of by each client remembering the rule correctly.

Cash requisition approval has no shared RPC at allTransactionDetailModal.tsx:188

Every CR status change (Approve/Decline) is a direct cash_requisitions.update() from mobile — there is no approve_cash_requisition-style RPC the way there now is for payments. If the web dashboard's approval flow does anything beyond the status write — a notification, an audit log entry, a validation the mobile client doesn't know about — mobile bypasses all of it today, invisibly.

ApproachSame treatment as payments: a shared update_cr_status (or similar) RPC that both clients call, so approval behavior can't silently diverge between web and mobile.

CR approval may never post to financial_transactions from mobilefinancial_transactions is read-only in mobile

Mobile never inserts into financial_transactions — confirmed, every reference to that table in src/ is a read. That means approving a CR from the mobile app relies entirely on something else (a database trigger, or web-only code) to create the matching expense ledger row. This is probably fine if a trigger exists — but it's worth confirming directly, because if it doesn't, every CR approved from a phone in the field quietly never shows up in Finance until someone also touches it from the web.

ApproachVerify server-side whether a trigger creates the ledger entry on CR approval. If not, the same RPC recommended above should write both rows atomically — exactly the "one transaction, one function" shape record_payment already established.

Unbounded queries on tables that only grow5 locations

useNotifications.ts:72 fetches every notification a user has ever received with no limit (the code comment literally says "Fetches ALL notifications once"). useBookingsData.ts:37 fetches every booking ever made when the status filter is "all." SafariManagementScreen.tsx:1216, 2417, 3136 each fetch the entire safari_bookings table with no date bound or row cap, for the Bookings tab, the Analytics tab, and the Payments tab respectively.

ApproachAdd a sensible .limit() everywhere (the Finance hooks already do this correctly — 100-500 rows depending on filter) and prefer narrowing by date range over fetching everything and filtering client-side.

Notifications and exchange rates each run 2-3 redundant realtime subscriptionsuseNotifications.ts · useExchangeRate.ts

useNotifications(userId) is independently invoked from the app root, from the header's notification bell, and from the Notifications screen itself — all three typically mounted at once, each running its own unbounded fetch and opening its own realtime channel literally named notifications-${'{'}userId{'}'}. useExchangeRate() has the same issue between Dashboard and Finance — two channels both named exchange-rates-changes running concurrently. Both tables are even already listed in realtimeManager.ts's ALL_TABLES array, which bookings/fleet/finance/dashboard all correctly route through — notifications and exchange rates just never got wired in.

ApproachRoute both through the existing realtimeManager the same way the other four data hooks already do — the shared-channel infrastructure is already built, these two just need to use it.

Offline network detection is built but completely unwireduseNetworkStatus.ts

The hook exists, works, and is exported — but nothing in the app imports it. No offline banner, no gating on write actions, nothing. For a safari ops app whose users are routinely inside national parks with no signal, a visible "you're offline" state is one of the highest-value things in this list and it's sitting there half-built.

ApproachWire it into a persistent banner at the app shell level, and surface it specifically on the payment-recording and CR-submission screens where a silent failure is most costly.

No retry queue for failed writes while offlineApp-wide

record_payment's idempotency key protects against double-submission on a manual retry, but there's no automatic resubmission — if a guide records a payment with no signal, it just fails, and the amount isn't captured anywhere until they remember to try again with connectivity. There's no AsyncStorage-backed queue for failed mutations anywhere in the app; AsyncStorage today only holds auth state, preferences, and read-through cache.

ApproachOnce the offline banner above exists, the natural next step is queuing failed payment/CR submissions locally and replaying them automatically when useNetworkStatus reports back online.

Two conflicting definitions of SafariBookingtypes/dashboard.ts:123 · types/safari.ts:5

One file defines a minimal financial-only shape (no status, no booking_reference); the other defines a rich operational shape with joined relations. Nothing currently imports the wrong one, but same name, same project, two different shapes is exactly the setup for a future edit to autocomplete into the wrong import and compile against fields that don't exist on the record actually being passed in.

ApproachRename one — e.g. SafariBookingSummary for the dashboard.ts financial shape — so the name itself signals which one a new piece of code should reach for.

No shared error-message formatter25+ call sites

Every screen rolls its own Alert.alert('Error', e?.message || 'fallback text') — consistent in style, but duplicated 25+ times with no shared helper. SafariManagementScreen.tsx even has its own inline isSchemaErr check reinventing "is this a Postgres schema-cache error" logic that would belong in that same shared helper.

ApproachA single getErrorMessage(e, fallback) utility would collapse all of these and become the natural place to translate raw Postgres error text into something a non-technical user can act on.

Harmless duplicate: CacheEntryuseGA4Analytics.ts:109 · useGoogleAds.ts:77

Same name, different shapes, both non-exported and scoped to their own file — no cross-import risk, unlike the SafariBooking case above. Flagging only for completeness; not worth touching on its own.

CR cancellation has no write path at allcash_requisitions

Approve and Decline both exist; there is no "Cancel" status write anywhere in the mobile app for a CR that's no longer needed. Worth confirming whether this is intentionally web-only or simply missing.
