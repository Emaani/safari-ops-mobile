Improvement Roadmap

A prioritized set of fixes and features across Dashboard, Fleet, Finance, Bookings, Safari Management, Marketing, and Notifications — assessed against how the app is actually used to run daily safari operations.

25 recommendations 7 screens reviewed Generated 28 Sep 2026

Where the app stands today

The foundation is solid — Expo SDK 54, Supabase with live real-time subscriptions on Dashboard, Bookings, Fleet, Finance and Safari, plus reanimated, victory-native charts, push notifications, biometric auth, and offline network detection all already installed as dependencies.

The gap is that several of these capabilities are installed but not fully wired into the day-to-day experience — offline detection has no banner, biometric auth isn't called on resume, push notifications don't deep-link anywhere, and a few screens quietly use stale data (fixed exchange rates, unbounded date ranges) that would mislead a manager glancing at a number.

7 items
Live exchange rate in Petty CashFinance

The PettyCash component hardcodes { USD: 1, UGX: 3700, KES: 130 } while everywhere else in the app pulls live rates via useExchangeRate. Petty cash totals shown in UGX or KES are calculated against a rate that may be months stale — a manager glancing at the number gets a wrong figure with no warning.

ApproachAccept a conversionRates prop matching the shape FinanceScreen already computes from useExchangeRate, and thread it down. No new network call needed.

Year/month filter for Finance recordsFinance

FinanceScreen fetches with no date filter and a flat .limit(100). For a company booking year-round, September records silently fall off the end of the list while January is unreachable — and totals can't be compared month-to-month against the Dashboard, which does filter by month.

ApproachReuse the month/year filter chips already built in DashboardScreen. Pass monthFilter/year into useFinanceData, add date-range clauses to the query, and drop the arbitrary row cap once the range bounds the result set.

Today's Operations BriefingDashboard

Dashboard shows monthly aggregates and recent bookings by creation date — but an ops manager opening the app in the morning most urgently needs to see what's departing today, what's currently in the field, and which vehicles are out. None of that is surfaced anywhere.

ApproachAdd a horizontal-scroll widget between Quick Actions and the KPI grid: filter bookings where start_date = today or status = 'in_progress' (already in state). Card shows vehicle plate, client, destination, pax, guide — tap to open Bookings.

Insurance & service-overdue alertsFleet

useFleetData already fetches insurance_expiry, last_service_date and next_service_date for every vehicle, and these show inside the detail modal — but nothing surfaces them proactively. A vehicle going out with lapsed insurance is a legal and safety exposure, not just a data gap.

ApproachAdd a "Needs Attention" section at the top of Fleet filtering vehicles with insurance expiring within 30 days (or already expired) or an overdue next_service_date. Surface a count badge on the Fleet tab via tabBarBadge. No new fetching required.

Record Payment from Outstanding PaymentsDashboard

The Outstanding Payments modal is read-only. Seeing which bookings have a balance due but having no way to act on it means staff read the list, then navigate to Bookings, find the booking again, and open its detail — for a task performed dozens of times a week.

ApproachAdd a "Record Payment" button per row that opens an inline sheet — amount, currency, method. On save, update amount_paid on the booking and refetch. The fields already exist on the Booking type.

Strip raw console.log from production hooksApp-wide

useFinanceData and useFleetData log fetch activity directly with console.log — including financial totals and vehicle records — which persists into production device logs. A gated devLog helper already exists and is used elsewhere in the codebase.

ApproachSearch-and-replace remaining console.log/console.error calls in hooks with devLog, confirming it's gated on __DEV__. Small change, real exposure closed.

Push notification deep-linkingNotifications

expo-notifications is installed and a notification service exists, but nothing registers addNotificationResponseReceivedListener anywhere in the app. Tapping a push for a new booking or an approved CR just opens the app at whatever screen was last active.

ApproachRegister the listener at the app root; parse notification.request.content.data for type/id and navigate accordingly. Notification types are already catalogued in NotificationsScreen's TYPE_EMOJI map.

Fix the wrong brand palette in constants/colors.tsApp-wide

src/constants/colors.ts defines primary: '#3b82f6' — a blue — while every screen actually uses the warm bronze #8B6B3E via its own local color object. The shared constants file is simply wrong and unused; any future brand tweak means editing seven screens individually.

ApproachCorrect the constants file to the real palette, then wire each screen to import from it via a shared useThemeColors() hook — which also opens the door to dark mode later.

Calendar view for BookingsBookings

A date-sorted list doesn't show how loaded a given week is or where the gaps are. Safari bookings run 4–8 weeks out — staff currently cross-reference manually to judge availability for a new request.

ApproachAdd a Calendar/List toggle with a month-strip that highlights booking-count per date; tapping a date filters the existing list. Uses data already in state — no new fetching.

UWA permit reference & confirmation trackingSafari Management

The permit catalog covers Gorilla and Chimp permits with a booking join table, but there's no field for the Uganda Wildlife Authority's actual booking reference, and no way to mark whether UWA has confirmed it. An unconfirmed gorilla permit costs the client their trek — this is the single highest-stakes data gap in the app.

ApproachAdd external_reference and authority_confirmed to safari_booking_permits. Show both inline in the booking's Permits section, and flag any booking with an unconfirmed gorilla/chimp permit in red.

Share booking confirmation as PDFBookings

There's no way to generate a client-facing confirmation from the mobile app. WhatsApp is the default communication channel in east African safari operations, and staff need to send a formatted summary on the spot, not from a desktop later.

Approachexpo-print renders a simple HTML template with booking details; expo-sharing (already installed) sends it straight to WhatsApp. Add a "Share Confirmation" button on the booking detail.

Odometer update from the fieldFleet

Odometer readings are fetched and displayed but there's no way to update them from mobile — only from the web dashboard. Service-interval tracking, insurance claims, and driver accountability all depend on this being current.

ApproachAdd an "Update Odometer" action in the vehicle detail modal — numeric input pre-filled with the current reading, writes back with a timestamp.

Client lookup screenNew screen

Clients are referenced everywhere — client_id, company name, contact — but there's no screen to pull up a client's history, contact info, or lifetime spend. When a repeat client calls to book, staff have no way to check their record from a phone.

ApproachNew screen (reachable from More or the client name on a booking) querying clients with search: company, contact, total bookings, total spend. Tap through to all bookings for that client.

Expose promotion start/end dates in the create formMarketing

The Promotion type already carries start_date/end_date, but the creation form doesn't appear to expose them — so promotions can't be pre-scheduled for Christmas gorilla treks or Easter safaris and must be manually flipped live at the right moment.

ApproachAdd date pickers (@react-native-community/datetimepicker is already installed) to the promotion form, and show a live/upcoming/past indicator on each promotion card.

Unread badge + mark-all-readNotifications

There's no badge on the Notifications tab, so a new booking or CR approval gives no visible signal on the tab bar — and after a busy day, dismissing notifications one by one is tedious.

ApproachExpose the unread count from useNotifications to the tab navigator's tabBarBadge. Add a "Mark all read" header action doing one batch update.

Resolve the SafariScreen / SafariManagementScreen overlapBookings · Safari Mgmt

Two screens cover overlapping ground — a simpler SafariScreen list view and the full four-tab SafariManagementScreen. It's unclear which is actually reachable from the tab bar; maintaining both risks staff landing on the wrong one and doubles the surface area for every future fix.

ApproachAudit the navigation config to see which is live. Either fold SafariScreen in as a sub-view of Safari Management's Bookings tab, or remove it outright.

Remove the dead && false loading overlayDashboard

DashboardScreen has a loading condition that ends in && false, permanently disabling the overlay — almost certainly a leftover patch for a rendering bug that was never actually resolved. It reads as intentional but silently does nothing, which misleads whoever touches this code next.

ApproachEither delete the dead conditional entirely, or diagnose the original rendering issue and replace it with the KpiRowSkeleton pattern already used elsewhere on the same screen.

Visible offline banner + action queueApp-wide

Guides and drivers routinely lose signal inside Bwindi, Queen Elizabeth, or Murchison Falls. useNetworkStatus correctly tracks connectivity but isn't wired into any visible UI — a write attempted offline currently just fails silently.

ApproachStart with a persistent amber "You're offline — changes will sync when reconnected" banner. Follow with queuing critical writes (payment records, status updates) in AsyncStorage and replaying on reconnect.

Guide availability calendarSafari Management

Assigning a guide to a new booking gives no indication they're already committed to another safari on overlapping dates — a real double-booking risk when several safaris run concurrently.

ApproachAdd a monthly strip in the guide detail view highlighting confirmed assignment dates, and a conflict warning in the guide picker when selected dates overlap an existing booking.

Vehicle booking availability calendarFleet

Determining whether a specific vehicle is free for a new hire request currently means manually cross-referencing the Bookings screen — there's no at-a-glance view per vehicle.

ApproachAdd a booked-date-range calendar strip to the vehicle detail modal, querying both bookings and safari_bookings by vehicle id.

UTM link generatorMarketing

useUTMTracking exists and GA4 source data is already surfaced, but there's no way for staff to generate a trackable link for a WhatsApp campaign or agent referral email — so that traffic just shows up as "direct" in GA4, undermining the analytics that already exist.

ApproachAdd a small form — destination page, source/medium/campaign — that builds a UTM URL and shares it via the native Share sheet.

Pre-trip vehicle checklistFleet · Bookings

East African safari vehicles are legally required to carry specific equipment — fire extinguisher, first aid kit, valid insurance card, yellow fever certificates — and there's currently no pre-departure confirmation step in the app.

ApproachA checklist template table in Supabase; the assigned guide checks off each item with a timestamp before departure, creating an audit trail for incident investigations.

Day-by-day itinerary builderSafari Management

A safari booking captures start/end dates, pax, and a package reference — but the actual day-by-day plan (Day 1: Entebbe → lodge, Day 2: gorilla trek) lives entirely off-system, so agents can't share or track it from the app.

ApproachAdd an itinerary_days field (or linked table) and a simple day-editor in the booking detail — location/activity per day, rendered as a read-only timeline in the overview.

Biometric lock on app resumeApp root

expo-local-authentication is installed but not wired up anywhere. On a shared device or one left unattended, anyone can open the app straight to live financial figures.

ApproachOn AppState returning to foreground after 5+ minutes backgrounded, require Face ID / fingerprint before rendering screen content.

Driver management screenFleet

Drivers are referenced on vehicle records but have no screen of their own — no way to check license expiry, see a driver's trip history, or find a backup when a regular driver calls in sick.

ApproachAdd a Drivers sub-tab to Fleet querying the existing drivers table: name, phone, assigned vehicle, license type/expiry, linked trip history.
